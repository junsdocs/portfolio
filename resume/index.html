2. 대표 성과

2-1. 팀원 IT 지원과 반복 업무 제거 (운영팀 2년)

반복 문의를 그때만 답하지 않고, 원인이 되는 작업 자체를 도구로 없앴습니다.

상황 — 팀원 문의의 상당수가 같은 질문의 반복이었고, 그 뿌리는 고객 응대 한 건마다 여러 SaaS를 뒤져 값을 옮겨 적어야 하는 구조였습니다. 개선을 지시받은 적은 없습니다 — 제가 불편해서 스스로 기획하고 만들기 시작한 일입니다.

수행

  • 반복 문의가 나오는 작업을 골라 도구화 — 대표적으로 상담 안내문 자동 생성 도구는 딜 번호 하나로 약 30종 값을 자동 치환 (이전엔 CRM 여러 화면을 열어 옮겨 적던 작업)
  • 신규 입사자 계정·권한·도구 환경 세팅, 반복 안내는 위키 가이드로 정리(가이드·명세 7건)
  • 실행 환경 제약을 원인별로 해결 — 로컬 실행 차단 → 웹앱 이관(배포 방식 4회 전환) / macOS 격리 속성 → 해제 절차 가이드화 / 구버전 브라우저 → 전 코드 호환 재작성 / VDI 붙여넣기 제한 → 한 줄 압축·북마클릿 배포
  • 개인정보·토큰을 다루는 도구엔 접근 제어(도메인+허용목록) · 키 서버측 보관 · 사람의 최종 확인 게이트 · 사용 로그를 기본 탑재

결과 — 도구 10여 종이 팀·협력사 상시 도구로 정착. "반복 업무는 숙련도가 아니라 구조로 없앨 문제"라는 이후 설계 기준이 여기서 나왔습니다.

2-2. 계정·권한 거버넌스 — 정책 수립과 실행 도구

"누가 무엇을 쓸 수 있어야 하는가"를 활동 로그로 근거화하고, 정책을 도구로 고정했습니다.

상황 — 어드민 콘솔(활성 사용자 251명)에서 최고관리자가 22명. 역할이 직무 단위로 뭉쳐 있어 필요와 무관하게 과다 부여되는 구조였습니다.

수행

  • 권한 구조를 기능 69개 × 역할 64개로 분해하고 네이밍 규칙 정립
  • 90일 활동 로그 전수 분석으로 실사용 화면을 특정(커버리지 90.1%) → 해당 역할만 선부여 후 회수, 업무 중단 없음
  • 부여 API가 배열을 교체해 기존 역할이 소실되는 함정 발견 → 합집합 부여 + 스냅샷 백업으로 원복 확보
  • 관리자 부여 기준 4종을 정책으로 확정 (권한관리=부여 담당자만 / 감사로그=보안팀만 / 기능관리=개발자만)
  • 정책을 크롬 확장으로 고정 — 직무별 표준 권한 세트(5~19개)를 프리셋화. 확장은 선택까지만 하고 저장은 사람이, 클릭 후 실제 반영을 검증해 4상태로 보고
  • 권한 요청 접수 정형화 — 표준 필드 파싱 후 누락·권한 과다·계정 중복 검증

결과 — 최고관리자 22 → 3명, 직무형 역할 보유자 0명. 이후 권한 요청은 기준 대조만으로 처리.

재발방지 — 일괄 복제 중 보안팀 전용 역할이 7명에게 확산된 것을 직후 감지·전원 회수, "복제 시 감사로그 역할 항상 제외" 정책화. 유저 관리 화면 접근이 곧 역할 부여 가능(권한 상승 경로)인 구조 문제를 발견해 개발 과제로 이관.

2-3. 퇴직자 계정 회수 — 승인 파이프라인부터 무인화까지

승인·감사기록을 먼저 만들고, 앞단 감지를 붙여 사람 손을 뺐습니다.

상황 — 비활성화 요청이 대화로 오고 처리는 수동. 기록이 없고, 누락되면 퇴직자 계정이 살아 있는 채로 방치됐습니다.

1단계 (운영팀) — Slack 커맨드 → 관리자 승인 → API 실행 → 감사 로그 파이프라인 구축. 감사 스키마·상태 전이 정의, 증상별 진단표 9종 포함 매뉴얼 작성. 서명 검증 부재·자기 승인 가능 등 미비점을 스스로 우선순위와 함께 기재.

2단계 (제품팀) — 퇴직 티켓 흐름이 정착하자 기존 시스템을 한 줄도 수정하지 않고 앞단에 감지 계층만 추가(5분 주기). 티켓에서 대상자를 추출해 요청 / 완료 / 확인필요(자동 처리 금지)로 분기.

  • 핵심 설계: 상태를 저장하지 않는다 — 완료 판정을 "승인 횟수"가 아니라 "활성 계정이 남았는가" 로 매번 다시 판단 → 사람이 수동 회수해도 자동 종결

결과 — 첫 실전에서 전 구간 완주(수동 회수 21분 뒤 자동 감지·종결·알림). 상시 가동 중.

남긴 것 — 요청 채널이 외부 공유 채널이라 퇴직자 정보가 노출되는 구조임을 발견해 점검 과제로 등록. 2단계 착수 때 제가 만든 승인 시스템을 못 찾고 중복 구축했다 폐기한 뒤, "자동화 자산은 실물부터 확인" 원칙과 도구 인벤토리 관리를 시작했습니다.

2-4. 이슈 처리 체계 — 증거 확보, 판정 표준화, 정확도 실측

제보에 증거를 담게 만들고, 판정 기준을 고정하고, 정확도를 잰 뒤 투입했습니다.

상황 — 협력사에서 주 5~10건 오류 접수. 재현 정보가 부족하고 "어느 층 문제냐"부터 나누다 보니 오류가 아닌 건까지 티켓이 생성됐고(23건 중 7건이 "이슈 아님" 종결), 잘못된 보고를 근거로 만든 수정이 배포 직전 되돌려지기도 했습니다.

수행

  • 인테이크 — 제보 확장으로 기본정보 자동 수집 + 스크린샷 자동 압축 + 재현 직전 네트워크 로그 캡처로 "값이 틀렸다"를 검증 가능한 증거로 전환
  • 판정을 층보다 앞으로 — 6종 판정 후 "오류아님이면 티켓을 만들지 않는다" 규칙화, 도메인 편람 조회를 0단계로 강제
  • 투입 전 정확도 실측 — 정답 확정 60건 블라인드 검증으로 88% 확인. 선행 시도의 실패 5유형을 추출해 가드레일을 만들고 A/B 실험으로 전부 회피 검증. 잔여 오차의 주 원인은 계산 모델 저장소 접근 권한 부재(60건 중 37건이 모델 층) — 접근 불가 영역에서는 추측하지 않고 멈추도록 절차에 명시
  • 판단 원칙 명문화 — "보고 내용은 주장이지 사실이 아니다" / "재오픈도 사실이 아닐 수 있다" / "문서와 티켓 댓글이 다르면 댓글이 우선"

결과 — 제보 → 판정 → 배정 → 회신이 담당자가 바뀌어도 같은 결론이 나오는 절차로 정착. 현재 상위 결재 없이 직접 판정·배정·회신하는 오너로 운영 중.

3. 그 외 수행 업무

SaaS 운영·보안

  • MFA 전사 강제 롤아웃 — 강제 레버 2개를 비교해 단계적 롤아웃이 가능한 프로필 방식 채택. 등록 현황 조회가 막힌 org에서 인증 이력을 프록시 지표로 우회 집계. 트러블슈팅 3건을 직접 재현·해결한 뒤 가이드에 반영, 관리자 12명 과다 지적·축소 제안
  • 팀별 화면 권한 분리 — 프로필 복제 배포에서 표준 탭 소실·버튼 화이트리스트 누락 2건을 실사용자 화면에서 발견·수정 → "탭 가시성 + 화이트리스트 스캔 + 타 사용자 시점 검증" 체크리스트로 고정

장애 대응·RCA

  • API 한도 소진 — 단일 인터페이스가 전체의 97% 소비, 원인은 다건 수신 지원 서버에 건별 호출하는 송신 구조. 묶음 전환으로 96.2% → 30%대. 계측 공백은 적응형 모니터(주기 자가 조절, 자체 소비 0.2%)로 메움
  • 타임존 오표시 — 원인이 저장 관례 2종 × 표시 관례 2종의 혼재임을 규명. 노출 22곳 + 데이터 오염 1건 특정, 선택지 3개 중립 제시, 운영 배포 완료
  • 연동 유실 감시 설계 — 한쪽 경로만 유실되면 결제 고객에게 독촉이 나가는 리스크. 이슈 4종을 비가역성 × 매출영향으로 등급화, 공통 대조 엔진 + 서킷브레이커 + 드라이런 → 반자동 → 자동 단계 전환 설계

운영 체계 표준화

  • 연동 자동화 39개 SOP — 알림 유실을 확인하고 감지 3중화(알림 / 이력 점검 / 미실행 필터 일일 마감). 재실행·폐기 판정 매트릭스 표준화, 재실행 전 실제 발송 이력 조회를 절차화(중복 발송 방지), SOP 작성 후 인수인계
  • 레거시 도구 → 사내 시스템 이관 — 시트가 DB였던 협력사 도구를 재구축. 운영 DB 읽기 전용 강제, 개발 환경 발송 차단, 환경 분리로 운영 리소스 접근을 구조적으로 차단
  • 제한 환경(VDI) 계정 처리 — 브라우저 콘솔 단독 실행 스니펫으로 비활성화 처리. 드라이런 → 역할 백업 → 확인 → 실행 → 검증 내장. 재활성화해도 역할이 복구되지 않음을 확인해 백업 기반 재부여 절차 문서화

자기소개서 — 사내 IT 운영 / IT Infra

지원 포지션: 팀원 IT 이슈 대응 · 사내 IT 인프라·업무 환경 운영 · IT 운영 자동화 및 정책 수립 · SaaS 운영

1. 왜 이 일인가

시작점 — 운영팀에서 가장 많은 시간을 쓴 일은, 고객 응대 한 건을 위해 여러 SaaS를 뒤져 값을 확인하고 복사·붙여넣기 하는 것이었습니다. 사람의 숙련도로 메울 문제가 아니라고 판단해, 문의를 받을 때마다 "이번만 답하는 것"과 "이 작업 자체를 없애는 것"을 나눠 보기 시작했고, 그렇게 도구와 자동화를 만들게 됐습니다. 누가 시킨 일이 아니었습니다 — 만들고 배포하고 정착시키는 것까지 스스로 정한 일이었고, 그것들이 팀의 상시 도구가 됐습니다.

왜 이 포지션인가 — 운영에 있을 때는 구조를 바꿀 권한이 없었습니다. 제품팀으로 옮겨 권한 체계·계정 회수·이슈 처리 절차를 실제로 바꿨지만, 제품팀에서 이 일은 곁가지입니다. 업무 환경을 설계하고 개선하는 것이 본업인 자리에서 두 관점을 함께 쓰고 싶습니다.

왜 토스인슈어런스인가 — 팀 소개의 "단순한 운영을 넘어, 자동화와 프로세스 개선을 통해 더 효율적인 일하는 방식을 만들어간다" 는 문장은, 지난 몇 년간 제가 해온 일의 정의와 같았습니다. 그리고 "모두가 맡은 바에 최종 의사결정을 한다" 는 문화는 — 지시 없이 스스로 시작해, 상위 결재 없이 판정·배정·회신까지 직접 해온 저의 일하는 방식이 표준인 곳이라는 뜻이라고 이해했습니다.

2. 일하는 방식

  1. 되돌릴 수 없는 작업엔 3종 세트 — 드라이런 / 백업·원복 / 실행 후 검증. 권한 부여·계정 비활성화·일괄 수정·대량 발송 모두 같은 원칙입니다.
  2. 자동화는 선택·수집까지만, 확정은 사람이 — 권한 부여 도구도 저장 버튼은 누르지 않게 만들었습니다.
  3. 상태를 저장하지 않고 매번 다시 읽습니다 — 사람이 수동으로 처리해도, 순서가 바뀌어도 결과가 같아집니다.
  4. 사고는 규칙으로 남깁니다 — 지금 쓰는 체크리스트·판정 기준 대부분이 실제 실수에서 나왔습니다. 제가 만든 것의 미비점도 매뉴얼에 먼저 적습니다.
  5. 개발팀에는 결론이 아니라 선택지와 트레이드오프를 줍니다 — 판단에 필요한 근거는 실측으로 준비합니다.

구현 방식 — 저는 개발자가 아니고, 도구의 코드는 AI 코딩 도구로 작성했습니다. 제가 한 일은 무엇을 만들지 정하고, 구조와 안전장치를 설계하고, 안 되면 원인을 끝까지 찾고, 실제 사용자에게 배포해 정착시킨 것입니다. 만드는 것보다 "그 사람 PC에서 돌아가게 만드는 것"과 "잘못 돌았을 때 되돌릴 수 있게 만드는 것" 이 실제 일의 대부분이었습니다.

3. 보완이 필요한 것

  • 사내 IT 인프라 실무 — 네트워크·디바이스·MDM 운영 경험은 없습니다. 배우면서 해야 합니다. 대신 반복 업무 인벤토리를 만들고 자동화 우선순위를 정하는 일은 첫날부터 기여할 수 있습니다.
  • IdP 중심 계정 설계(Okta 등) — 현 조직에 SSO가 없어 운영 경험이 없습니다. 다만 권한 모델을 기능 단위로 분해하고 활동 로그로 최소권한 근거를 만든 경험이 그대로 쓰일 영역이라고 봅니다.
